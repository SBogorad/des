**Date:** 2026-07-08

## Executive Summary

**Overall Assessment:** ⚠️ **Production-Ready with Medium-Priority Improvements Needed**

The `rzd-des-engine` project demonstrates **strong technical foundations** with clean Rust architecture, deterministic simulation, comprehensive benchmarking infrastructure, and solid domain modeling. However, several **medium-severity concerns** require attention before the system can be considered fully production-grade for external deployment.

### Key Strengths ✓

1. **No critical security vulnerabilities** — no `unsafe`, no credential leaks, clean dependency tree
2. **Strong deterministic simulation** — reproducible benchmarks with SHA-256 verification
3. **Comprehensive testing** — 37+ tests, property-based testing, integration coverage
4. **Excellent documentation** — clear architecture docs, benchmark methodology, deployment runbooks
5. **Clean Rust practices** — zero clippy warnings (per CHANGELOG), no TODOs/FIXMEs
6. **Versioned contracts** — scenario/snapshot/trace schemas with explicit versioning

### Medium-Priority Concerns ⚠️

1. **Monolithic CLI** — 3,850-line `cli/src/main.rs` needs modularization
2. **Missing CI validation** — no automated clippy/test runs, deployment is manual
3. **Untracked dead code** — `memory_pool.rs`, `errors.rs::RzdError`, `whatif.rs` appear unused
4. **Export performance gap** — CED JSON export takes 26–153 seconds vs. <1s simulation
5. **Visualization coupling** — demo site hardcoded to specific crew/scenario URLs
6. **Missing SBOM/provenance** — no supply chain attestation for contest bundles

5. **No rate limiting** — visualization demo has no DDoS protection (static site)

// 2. Sanitize output paths in CLI
fn sanitize_output_path(user_path: &Path) -> Result<PathBuf, SecurityError> {
    let canonical = user_path.canonicalize()?;
    if !canonical.starts_with(&std::env::current_dir()?) {
        return Err(SecurityError::PathTraversal);
    }
    Ok(canonical)
}

### 🔴 Critical Architecture Issues

#### 1. Monolithic CLI (3,850 lines)

**Problem:** `cli/src/main.rs` contains:
- 14 subcommands with inline implementations
- Bundle generation, comparison, leaderboard logic
- Export rendering (CED, TU-3, trace)
- Progress tracking, SHA-256 hashing, file I/O
- Embedded test suite (375 lines at end of file)

**Impact:**
- Impossible to unit test individual commands
- High cognitive load for maintenance
- Difficult to add new export formats or commands
- Violates single responsibility principle

**Recommended Refactoring:**

```
cli/src/
├── main.rs              [100 LoC - arg parsing only]
├── commands/
│   ├── mod.rs
│   ├── run.rs
│   ├── benchmark.rs
│   ├── bundle.rs
│   ├── compare.rs
│   └── checkpoint.rs
├── export/
│   ├── mod.rs
│   ├── ced.rs
│   ├── tu3.rs
│   └── trace.rs
└── util/
    ├── progress.rs
    ├── hash.rs
    └── validation.rs
```

**Estimated effort:** 2–3 days for clean extraction with preserved behavior.

## Benchmark & Competition Readiness

### 🟢 Strong Competition Story

1. **Reproducible bundles** — manifest.json with SHA-256 hashes for all artifacts
2. **Deterministic signatures** — `business_signature` stable across repeats
3. **Shoulder-aware metrics** — A/B/C breakdown for regional analysis
4. **Trace comparison** — structured drift classification (timing vs. business)
5. **Scale ladder** — 8 profiles from demo to RZD-scale (750k violations)

### 🟡 Missing Competition Requirements

1. **SBOM (Software Bill of Materials)**
   - No `cargo-sbom` or SPDX manifest
   - Judges cannot verify dependency provenance

2. **Reproducible build instructions**
   - README shows commands but not exact Rust/Node versions
   - No Docker build for hermetic compilation

3. **External validator**
   - No independent script to verify bundle SHA-256 matches
   - Judges must trust CLI output

4. **Comparison justification**
   - `comparison.json` shows deltas but not *why* (e.g., "shoulder A added 95k events because X")

**Recommended Additions:**

```bash
# 1. Generate SBOM
cargo install cargo-sbom
cargo sbom > SBOM.json

# 2. Add to bundle manifest
{
  "sbom": "SBOM.json",
  "sbom_sha256": "...",
  "rust_version": "1.96.0",
  "build_timestamp": "2026-07-08T12:00:00Z"
}

# 3. External validator script
#!/usr/bin/env python3
# verify_bundle.py - independent hash verification
import json, hashlib
manifest = json.load(open('manifest.json'))
for artifact in manifest['artifacts']:
    actual = hashlib.sha256(open(artifact['path'],'rb').read()).hexdigest()
    assert actual == artifact['sha256'], f"{artifact['path']} hash mismatch"
```

## Conclusion

The `rzd-des-engine` project is **well-architected and functionally complete** for its core mission: deterministic railway crew simulation with reproducible benchmarks. The codebase demonstrates strong Rust practices, comprehensive testing, and excellent documentation.

However, **production readiness requires addressing the monolithic CLI structure and export performance bottleneck**. The 3,850-line `main.rs` makes maintenance difficult and testing impossible, while 27–153 second export times dwarf the <20 second simulation runs.

**Recommended Next Steps:**

1. Refactor CLI (2–3 days) — unlocks testability and maintainability
2. Optimize exports (1–2 days) — eliminates user-facing performance gap
3. Add CI benchmarks (1 day) — prevents future regressions
4. Generate SBOM (0.5 days) — enables contest submission

**Estimated total effort:** ~5–7 days to reach full production readiness.

**Overall Grade:** **B+ (Production-Ready with Improvements)**

- Core engine: **A** (clean, fast, tested)
- CLI & tooling: **C+** (functional but needs refactoring)
- Documentation: **A** (excellent architecture docs)
- Testing: **B** (good coverage, needs CLI tests)
- Performance: **B+** (simulation fast, export slow)
- Security: **A-** (no vulns, minor hardening needed)
